# GameCoach — Product Vision & Skill Architecture

整理日期：2026-10-18。

这份文档记录项目的长期愿景、已确定的设计原则和建议的实现顺序。这里描述的未来能力不代表已经完成。当前使用方法和已实现功能见 [README.md](./README.md)。

## 1. 产品要解决什么问题

GameCoach 的目标是成为一个理解游戏背景、记得用户情况、能够跟随对局过程的游戏教练。用户可以讨论阵容、上传战绩、复盘录像、一起看比赛，长期再探索自己对局中的实时辅助。

产品价值应体现在具体体验上：

- 少填写：阵容、玩家资料和已确认的对局信息可以自动成为相关问题的背景。
- 少重复：同一个聊天中保留必要的历史，能根据“刚才的方法不行”等反馈调整建议。
- 能执行：先给当前问题的结论或行动，再解释原因和条件。
- 能查懂：回复中的英雄、装备、属性、选手、战队等名称可以展开资料卡。
- 可比较：同类评分使用同一套明确标准，有依据、有版本，方便回看。
- 成本可控：尽量在本地完成重复识别、筛选和资料展示，只把必要信息交给模型。

这些是待验证的产品目标，不预设已经优于其他产品。

## 2. 当前实现与长期目标的边界

| 部分 | 当前状态 | 后续目标 |
| --- | --- | --- |
| 前端 | HTML、CSS、JavaScript；聊天、Markdown、BP、游戏切换、本地用户 | 图片、语音、资料卡、评分、观看与复盘入口 |
| 游戏资源 | `lol`、`lolm` 英雄目录和本地头像 | 有来源及版本的技能、装备、属性、赛事、选手与战队资料 |
| 游戏扩展 | 端游与手游可切换；王者荣耀、Dota 2 是未开放的展示项 | 为不同游戏接入各自的资料、识别和规则 |
| `ai-core` | 通用模型调用、Gemini、流式回复、执行配置、取消和超时 | 保持模型适配边界，按实际需求扩展多模态能力 |
| `skill` | 透传占位；收到的 BP、用户 context 暂未加入模型输入 | 信息选择与压缩、评分、输出整理、资料关联 |
| 用户数据 | 浏览器本地保存，可连接用户文件夹及导入导出；`users/` 被 Git 忽略 | 用户可查看、修改和删除长期偏好、训练目标与记录 |
| 视觉、语音、持续对局记录 | 尚未实现 | 截图识别、语音输入、录像分析、持续观看 |
| `back-end` | 占位 | 仅在确实需要服务端能力时实现 |

当前 API Key 仅保存在页面内存。后续设计不能把它混入用户资料、对局记录、日志或仓库资源。

## 3. 核心原则

### 3.1 足够的信息，尽量少的 Token

这是 Skill 输入端的首要原则。先保证事实、问题和必要上下文完整，再减少无关、重复和冗长的内容。不能声称已经达到数学意义上的最少 Token，也不能用丢失关键条件来换取更短输入。

### 3.2 模型与游戏业务分开

`ai-core` 接收通用文字、消息及适配器支持的多模态内容，不要求输入必须是某种游戏表格。Skill 负责把游戏与用户的补充信息组织进去。

Quick / Coach 通过模型、思考额度、输出额度等执行配置切换。选用哪个模型、怎样传递这些参数，由 `ai-core` 负责；Skill 不靠一句“请快速回答”代替执行配置。

### 3.3 每个能力有独立职责

CV、OCR、语音、对局记录、评分、输出整理都可以独立实现。Skill 负责选择和串联需要的步骤，避免所有功能都堆在一个大文件中。下面的模块划分是职责设计，不要求现在就创建全部目录或占位文件。

### 3.4 事实、推断与未知分开

识别结果要保留来源、时间和可信程度。模型推断不能直接覆盖观察到的事实。识别不了、资料缺失或证据不足时，应明确缺少什么，允许用户纠正。

### 3.5 附加 AI 调用必须有用途

轻量 AI 可以用于摘要或文字整理，但不是每次请求的必经步骤。额外调用的 Token、费用和等待时间应计入整条链路。能通过代码、模板和词典完成的处理，优先使用这些方式。

## 4. 整体职责与数据流

| 部分 | 输入 | 输出及职责 |
| --- | --- | --- |
| 前端与采集 | 用户操作、文字、图片、语音、用户授权的画面 | 提交用户原始内容，展示结果，提供纠错入口 |
| 识别模块 | 截图、画面、音频，或可用的游戏数据接口 | 提取文字、英雄、装备、比分、时间等观察结果 |
| 对局记录 | 有时间与来源的观察结果、用户确认的信息 | 当前状态、相关事件和必要的历史快照 |
| Skill 输入处理 | 用户输入、历史、BP、玩家资料、对局状态 | 相关、去重、紧凑的模型输入；需要时携带评分标准 |
| AI Core | 通用输入和执行配置 | 主模型的分析、流式文本和调用元信息 |
| Skill 输出处理 | 主模型结果、评分规则、输出偏好 | 可选评分、可选文字整理、资料引用 |
| UI | 文字、分数、引用、状态 | Markdown、评分卡、悬浮详情，后续可扩展语音播报 |

基本调用链仍然是：

```text
前端 → skill 准备输入 → ai-core → skill 处理输出 → 前端
```

未来的识别与对局记录为 Skill 提供额外信息，不限制用户只能通过这些方式提问。

## 5. Skill 输入端

### 5.1 输入内容

- 用户当前原话，以及未来的图片、语音转写等内容。
- 当前问题需要的聊天历史。
- 游戏、版本、蓝红双方选人、Ban，以及明确指定的位置。
- 已填写或确认的用户资料：段位、常用位置、熟悉的英雄、偏好等。
- 未来识别出来的战绩、对局状态、事件与时间。

第一版的基本任务是接通 BP 和相关用户资料，输出端继续原样转交。用户没有选择阵容时，依然可以正常聊天。

BP 的选人顺序不能自动当作分路；没有明确的分路信息时，不把第一个英雄直接解释为上单。

### 5.2 输入压缩顺序

1. 判断本次问题需要哪些资料；第一版可先固定携带一份简短 BP，其他资料逐步按需选择。
2. 选择对应游戏与版本，提取相关字段。
3. 去除重复资料、无关字段、文件路径及纯 UI 状态。
4. 用固定、简短的格式组织补充信息，保留用户当前原话。
5. 控制历史长度；近期保留必要原文，较早内容在需要时生成摘要。
6. 检查是否超出输入预算，再交给 AI Core。

简短 BP 示例：

```text
游戏：英雄联盟手游
蓝选：卡尔玛、露露、娜美、蕾欧娜、金克丝
红选：凯特琳、阿卡丽、易大师、墨菲特、潘森
```

有 Ban 时添加对应行；没有时省略。需要位置、版本等条件时再补充。不要只发内部英雄 ID，再附一大份 ID 翻译表。

### 5.3 历史、变化与用户记忆

每条消息保留发送当时的阵容快照，之后的修改不能覆盖旧消息。模型输入不必把每条历史消息相同的 BP 重复展开；比较前后阵容时，才引入相关旧快照。

持续对局信息可以在本地记录变化。由于模型调用本身不自动持有上次请求，发送增量时必须同时给出足够的当前状态或必要摘要，让这一条请求能够独立理解。

用户偏好与训练目标应可查看、修改和删除。需要用户确认的长期记忆，不能仅因一句临时抱怨就永久写入。

### 5.4 成本与质量检查

- 记录 BP、用户资料、历史、检索资料等输入来源的占用估算。
- 能取得 API 实际用量时记录实际值；字符数不能冒充准确 Token 数。
- 统计主模型及额外摘要、整理调用的总消耗和延迟。
- 对照压缩前后请求，检查英雄归属、关键条件、用户问题是否保留。
- 不把隐藏的模型思考过程作为输入压缩或调试日志的依赖。

### 5.5 可逐步验证的教练体验

除了 BP 输入，还可以探索以下功能，具体 UI 尚未定稿：

- 用户明确“这局我玩谁、什么位置”，让建议优先落到自己的操作与决策上。
- 用少量快捷事件补充“被连续抓”“后排被切”等情况，减少比赛中打字的负担。
- 用户反馈方法无效或局势改变时，调整已有计划，而不是重复基础建议。
- 赛后 Coach 提出一个用户认可的练习目标 → 下一局 Quick 带着这个目标给建议 → 赛后根据实际反馈检查改善情况。

这些功能需要观察用户是否少花时间描述、是否理解并能执行建议，再决定保留哪些。

## 6. 图片、语音与持续对局理解

### 6.1 截图识别

固定布局的战绩页适合作为第一种视觉任务：先定位区域，再识别英雄、装备、KDA、比分等实际可见信息。

- 英雄与装备图标：尝试模板匹配或其他轻量视觉方法。
- 数字与文字：通过 OCR 读取，必要时进行轻量识别与校验。
- 识别失败：保留未知或让用户纠正，不把猜测写成确定数据。
- 需要更复杂视觉理解时：再考虑把必要图片交给多模态模型。

CV / OCR 也有资源消耗。分辨率、缩放、语言、皮肤和界面更新会影响效果，应先限制支持的截图类型，再逐步适配。战绩图可以提供结果数据，不能凭一张图准确还原所有失误原因。

### 6.2 语音输入与输出

语音模块可以独立于 Skill：麦克风 → 语音转文字 → 普通消息入口。用户应能检查并纠正英雄名等转写错误。

以后可增加语音播报；播报应允许停止、控制长度，并避免持续打断用户。理解比赛音效或解说内容属于进一步能力，不与普通语音转写混为一项。

### 6.3 对局记录

持续观看需要同时保存当前状态与相关经过。建议每条观察包含：游戏与场次、时间、来源、读到的内容、可信程度和用户修正。

例如：比分从 5:4 变成 6:4，可以记录比分变化；没有看到击杀过程，就不能确定具体战术、位置或原因。画面切换、遮挡、回放和直播延迟也应影响状态的新鲜程度。

### 6.4 看比赛、看回放、看自己打游戏

| 场景 | 初步接入方向 | 需要验证的边界 |
| --- | --- | --- |
| 比赛直播 | 用户选择分享的比赛窗口，提取可见画面 | 转播布局、镜头切换、直播延迟、采集支持情况 |
| 录像与回放 | 用户提供片段或可播放内容，结合时间轴分析 | 输入格式、关键片段提取、时间对应；不承诺直接解析所有专用回放文件 |
| 自己的端游对局 | 研究官方 Live Client Data API，与必要的可见画面结合 | 实际可用字段、本地连接方式和官方允许的辅助范围 |
| 自己的手游对局 | 单独研究可用的画面或官方数据来源 | 不能直接假定存在与端游相同的接口；手机画面怎样进入电脑也要单独解决 |

实时分析不应默认把每一帧都发给大模型。可在本地识别并更新状态，在用户提问或有意义的变化发生时按需触发分析，并限制重复触发。具体采集频率、端到端延迟和成本由原型实测决定。

“打排位 / 看比赛 / 复盘”是使用场景；“Quick / Coach”是模型执行档位。两者可以分别存在。场景按钮、段位选项的具体 UI 尚未定稿，不作为本阶段已决定要添加的界面。

## 7. 输出一：由 Skill 统一计算的评分

### 7.1 职责

用户希望 AI 提供定性分析和解释，再由 Skill 根据评分模块计算分数。为减少自由文字的歧义，建议解释同时带有固定判断标签，而不是从“不错”“很强”等形容词中猜分。

```text
维度：开团能力
判断：有条件成立
依据：具备先手手段，但需要队友及时跟进。
```

维度和判断标准由 Skill 提供；AI 根据证据选择判断并解释；分值映射、权重和总分由 Skill 的规则计算。给模型的标准也应紧凑，仅发送本次适用的部分。

### 7.2 每套评分模块需要定义什么

| 项目 | 要回答的问题 |
| --- | --- |
| 评价对象与场景 | 评价的是阵容、局势、玩家表现还是一次决策？ |
| 维度 | 具体评价哪些方面？ |
| 标签及条件 | 哪些证据对应哪种判断？ |
| 分值与权重 | 判断如何转换成各项分数和总分？ |
| 缺失处理 | 哪些信息缺失时不能评分？如何展示暂评？ |
| 依据与来源 | 用户能否看见评分理由，区分观察和推断？ |
| 标准版本 | 历史评分使用的是哪一套规则？ |

同类对象在同一版本下使用一致标准；不同话题可以有不同评分表。即使都使用百分制，“阵容 80 分”和“个人表现 80 分”也不能直接比较。

信息不足不能当作表现差而计零分。不能在缺少重要维度时静默重新分配权重，制造看似完整的总分。

评分标准和映射结果可重复计算，但 AI 对证据的判断仍可能变化。提高一致性不等于自动保证准确性，需要用经过人工认可的案例校准，并保留可追溯的理由和版本。

具体维度、标签、权重及是否显示总分，尚待设计；本文不预先宣布某套分数已经可靠。

## 8. 输出二：可选的文字整理 Skill

输出整理可作为 Skill 内的独立模块。第一版保持原样返回；以后再增加代码模板或轻量 AI 处理。

可探索的样式包括一句话结论、行动清单、详细报告、比赛解说和评分卡。表达顺序优先考虑：先给结论或动作，再给原因和适用条件。

- 简单排版用代码或模板完成。
- 需要调整语言和组织逻辑时，再启用轻量 AI。
- 只向整理模型提供必要结论、已算好的分数和所需依据，避免再次传入整份聊天与资料。
- 整理可以改变表达，必须保留事实、分数、依据和不确定性。
- 附加模型的调用仍经过 `ai-core`，复用取消、超时、密钥及 provider 管理。
- 输出样式与 Quick / Coach 分开，不靠表达风格冒充更换模型。

直接返回路径继续支持流式显示。启用完整改写时，要明确等待与流式策略，避免原答案和改写版反复覆盖。Quick 默认不应被强制增加一次改写调用；新增处理不能让取消失效，或把旧请求结果写进新对话。

## 9. 输出三：名称识别与资料卡

最终回复中的英雄、装备、属性或机制、角色、选手、战队等实体，可以关联资料卡。桌面端鼠标悬停，移动端点击，键盘聚焦也能查看。

| 资料类型 | 可展示的内容，取决于实际已收集资料 |
| --- | --- |
| 英雄 | 头像、称号、定位、技能简介 |
| 装备 | 图标、价格、属性、效果、版本 |
| 属性与机制 | 含义、公式、限制及适用版本 |
| 选手 | 位置、所属战队、资料来源与更新时间 |
| 战队 | 队标、成员、赛事与资料来源 |

资源库保存资料；Skill 识别名称并关联稳定 ID；UI 展示卡片。可以先用本地词典与别称表，不要求额外调用 AI。

识别应在最终文字整理后进行。要结合游戏、版本和上下文处理歧义，优先匹配完整名称，避免短别称误命中普通词。无法确定时保留普通文字。不能破坏 Markdown 链接、代码或其他已有交互。

卡片资料按需读取，不随每条回答全部发送给模型。可先只标记同一段首次出现的名称，使用柔和提示，保持聊天清爽。内容缺失或版本不符时应展示实际状态，不编造详情。

## 10. 输出组合与接口方向

按本次问题选择需要的步骤：普通聊天可以直接返回，评分请求才启用评分模块，指定表达样式时才启用整理。资料关联在最终文字确定后进行。

```text
Skill 选择资料与评分标准
  → 主模型分析
  → 校验判断结果，按需计算分数
  → 按需整理表达
  → 识别名称并关联资料
  → 前端显示
```

未来输出可分成几类信息，具体接口尚未实现：

- 正文：最终文字与流式片段。
- 评分：对象、标准版本、各维度判断、分数、依据和缺失信息。
- 资料引用：实体类型、稳定 ID、展示名称、游戏与版本。
- 调用状态：完成、停止、失败、截断，以及能取得的用量和延迟。

评分结果单独保存；切换显示样式不重新评分。UI 保留原始正文和资料关联，不要求模型直接生成可执行 HTML。

## 11. 资源、本地数据与部署

共用英雄头像继续存放在 `resources/lol/champion-icons/`，手游独有头像放在 `resources/lolm/champion-icons/`。其他游戏建立自己的数据源，不能复用一套不适用的英雄、装备或评分规则。

未来的游戏资料要记录来源、游戏、适用版本和采集时间。图标、属性定义、装备效果、赛事资料可以分别维护，不能把一次快照称为自动更新的实时数据库。

个人资料、聊天、识别记录和训练目标以用户自己的本地存储为主，提供保存与导入导出方式。用户文件不放进公开资源目录，不提交仓库。浏览器访问本地文件夹仍需要用户选择授权，不能因用户打开网页就任意读写本机目录。

GitHub Pages 可继续承载静态前端。本地 CV、OCR、语音和画面采集的能力逐项验证；这不代表所有浏览器和设备都支持。将来连接本地游戏客户端时，可能需要本地辅助程序，是否需要云端后端另行决定。

本地识别不等于所有处理都离线；调用远端模型时，应明确发送哪些文字、图片或音频。输入预算还应区分文本 Token 与 provider 实际计算的多模态用量。

## 12. 建议实现顺序与完成标准

这是建议顺序，可以根据验证结果调整，不是所有能力必须依次实现的承诺。

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| 1. 接通基本 Skill | BP、游戏、相关用户资料的紧凑输入；输出透传 | 检查实际请求确实含有正确阵容；用户原话与历史保留；切换模式不丢上下文；不重复附加 BP |
| 2. 英雄资料卡 | 从已有英雄资源识别名称，关联资料卡 | 正确区分游戏与别称；桌面、移动和键盘可访问；不破坏 Markdown；不增加模型调用 |
| 3. 一套评分原型 | 先为一个明确场景定义维度、标签、映射及解释 | 用人工认可案例校准；相同判断重复计算得到相同分数；缺失、历史版本和引用依据可见 |
| 4. 固定战绩截图识别 | 先支持一种游戏、一种页面布局 | 在约定的截图集上记录字段准确率和失败案例；可纠错；确认前不把低可信数据当事实 |
| 5. 语音与可选输出整理 | 独立语音入口；按需文字整理 | 英雄名可纠正；改写不改变分数和事实；额外耗时与消耗可量化；停止请求仍有效 |
| 6. 片段复盘 | 带时间的录像片段与事件记录 | 能指出结论依据的时间位置；区分观察与推断；有限片段不会被说成完整对局 |
| 7. 持续观看与实时探索 | 画面或官方数据接入、状态变化与按需分析 | 实测识别质量、数据新鲜度、端到端延迟、误触发和总成本，再决定支持哪些场景 |

每阶段先形成可验证的完整流程，再扩大游戏、界面和能力范围。现在不同时实现全部识别、评分、记忆、轻量 AI 和实时采集。

## 13. 仍需决定的问题

- 第一套评分到底评价什么，谁来确认参考案例，怎样定义“好”的判断？
- 第一种视觉任务支持什么截图、分辨率和语言？
- 长期用户记忆保存哪些内容，什么时候请求确认，怎样修改或删除？
- 单次输入及整条链路允许多少消耗，哪些请求值得追加一次模型调用？
- 实时分析是主动提醒还是用户提问后回答，允许多频繁地打断用户？
- 资料从哪里收集、怎样更新版本、缺失资料怎样展示？
- 语音、本地采集和客户端接入分别选择什么实现？

## 14. 技术依据与限制

以下文档用于评估实现路径，不代表项目已经完成接入；落地时需要再次核对实际可用性。

- [OpenCV.js 模板匹配](https://docs.opencv.org/4.x/d8/dd1/tutorial_js_template_matching.html)：可用于验证固定图标的图像匹配方案，不能据此保证复杂界面识别率。
- [Tesseract.js](https://github.com/naptha/tesseract.js)：浏览器或 Node.js 的 OCR 选择之一，游戏字体与小数字需要实测。
- [浏览器屏幕采集](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia)：需要用户主动操作和授权，在支持的浏览器及安全上下文中使用。
- [Riot Live Client Data API](https://developer.riotgames.com/docs/lol#live-client-data-api)：提供本地进行中端游对局的一部分游戏与玩家数据，不等同于任意直播的完整比赛数据。
- [Riot Replay API](https://developer.riotgames.com/docs/lol#replay-api)：主要提供回放播放、镜头等控制，不直接提供完整战术理解。
- [Riot 游戏使用规则](https://developer.riotgames.com/docs/lol#game-integrity)：对局内辅助应依据允许的数据与行为范围设计；观看比赛、赛后复盘和排位中的实时辅助需要分别评估。
